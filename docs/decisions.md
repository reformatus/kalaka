# Decision log

The authoritative record of decisions. A decision lands here when the owner
makes or confirms it. Later decisions may refine or supersede earlier ones;
the later entry says so. "Architecture §N" refers to the
[architecture page](architecture.md). Names of plugins, modules, hooks and
code identifiers are placeholders.

| D-028 | 2026-10-23 | **Registration does not require a WordPress account.** Editing an account's profile never changes an existing registration. Without an account, a personal secret link opens the registration's status page, including payment status. A WordPress account is an extra layer that **owns** registrations: it can hold several people (guardian, youth leader registering a group), register them for several events (e.g. both REFISZ camps), see all outstanding balances together and **pay them at once**. **Participants must be trackable year to year** | Editability refined by D-035. Architecture §4 |
| D-029 | 2026-10-23 | **Identity model, in core:** a WordPress account owns 0..n **people** (stable identity across years; editable profile used for prefilling); registrations made for one of these people are linked to them and tracked year to year. People can be transferred between accounts. **Guest registrations create no person record and are never matched**: guest registration is deliberately semi-anonymous and untracked, and organizers get no manual linking tool. A guest may later attach their registration to an account via its secret link. An account can pay all its registrations in one order, split into each registration's ledger | Architecture §4 |
| D-030 | 2026-10-23 | **A registration is for exactly one event.** Attending two events (e.g. both REFISZ camps) means registering twice; an account can reuse its saved person for the basic data, but the registrations are otherwise fully separate: own serial, status, secret link and ledger. **Budgets and accounting are completely separate per event** | Architecture §4 |
| D-031 | 2026-10-23 | **One form per event.** A form belongs to exactly one event; the event is fixed by which form is opened. An event may have several forms (e.g. participant and staff form, as today) | Supersedes the shared-forms part of D-010 |
| D-032 | 2026-10-23 | **Extension surface, by purpose:** anything that shapes behavior or money (fee components, payment guards, ledger line sources, conditions, portal sections, admin sections, form blocks, payment methods) goes through **typed PHP interfaces** registered with core. Reacting to what happened goes through **WordPress actions fired after the data is saved**, with stable documented names, open to any plugin | Architecture §6 |
| D-033 | 2026-10-23 | **Every action writes its audit entry together with its own changes**, so neither exists without the other | Architecture §2, §7 |
| D-034 | 2026-10-23 | **The WooCommerce integration is a separate extension plugin of ours** on core's payments interface; core has no WooCommerce dependency at all. Refines D-025 | Architecture §3 |
| D-035 | 2026-10-23 | **Registration data is editable per field.** Each form field defines whether it can be edited after submit, with locks by date/time or set manually. Organizers with the right permission can correct any field at any time. Registrants (via secret link or owner account) see all their submitted data and can edit the editable fields. The original submission stays as the unchanged record, and every edit is audited | Architecture §4 |
| D-036 | 2026-10-23 | **A person record is optional under accounts too:** a registration made from an account may be linked to a person or stay independent (untracked, like a guest). A youth leader can register a group without creating person records. **Default flows must be seamless:** guest registration, and "create account → person created automatically → register". Multi-person flows may be more involved, with short explanations | Architecture §4 |
| D-037 | 2026-10-23 | **Money uses WooCommerce-compatible shapes:** a currency code on every monetary record, decimals and rounding following WooCommerce conventions; multi-currency possible but not built. Cash and bank transfers are recorded by staff in core. **Payment methods are pluggable**, so more automatic methods can be added without changing core | Architecture §5 |
| D-038 | 2026-10-23 | **Secret registration links are stored readable**, so every email can carry the registrant's link. They are treated as secrets: never logged, masked in exports | Architecture §7 |
| D-039 | 2026-10-25 | **Per-event cost does not grow with the number of events.** Every table holding per-event data has indexes that start with the event ID, and every per-event list, sort and search query filters by event first. A MySQL integration test seeds many events and checks each per-event query's plan (`EXPLAIN`); a query that examines rows outside its own event fails the build | Sorting and searching one event's registrations must depend only on that event's registrations |
