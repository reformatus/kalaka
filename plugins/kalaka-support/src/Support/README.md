# Support

The organization directory, the congregation picker, the support offers and the congregation share: one extension plugin, `kalaka-support` (module `support`). It holds the directory, the congregation picker, the support offers and the share. The directory is a site-wide tree of typed nodes with an external ID, aliases and an active flag, imported from CSV, deactivated and never deleted.

Tables, created by the schema in `Module.php`: `kalaka_support_nodes`, written only by `NodeRepository`, `kalaka_support_offers`, written only by `OfferRepository`, and `kalaka_support_share`, written only by `ShareSettingsRepository`.

`Directory/` holds `Node` (the stored node), `NodeRepository`, the admin use case `SaveDirectoryNode` (`kalaka/save-directory-node`; needs full access), `NodeList` (the route's list), `NodeLookup` (the import's reads of stored nodes) and `NodeTreeQuery` (`ancestors()` and `descendants()`, one `WITH RECURSIVE` statement each).

Entry points: `Directory/Rest/NodesController` (`GET /kalaka-support/v1/nodes`, public, live nodes only, each with a `leaf` flag; `within` limits a search or a listing to the nodes below one node) and `Directory/Cli/DirectoryCommand` (`wp kalaka-support import <file>`, which runs the use case per node through `Directory/Cli/DirectoryImport`; the file has one column per level, headed by the level's node type, then optional `id`, `aliases` and `active`).

`Picker/` holds the congregation field: `CongregationFieldType` (the field type the module contributes; block `kalaka/congregation-field`, money-relevant and a path, `PathFieldType`; it stores the leaf's id with a snapshot of its path as JSON, gives the path's external IDs and the leaf's live name as its value, and opens a stored answer as the leaf's id), `PickedNodes` (its reads: whether a node is a live leaf, what a stored id names, a node's path, and what the picker shows of a current value) and `Blocks/congregation-field/` (`block.json`, `edit.js`, `render.php` through core's `Forms\Api\FieldMarkup`, with the answer the form opens with from `FieldMarkup::prefilled()`, and `view.js`, the combobox over the nodes route). The block is registered from `build/` (`npm run build`) by `Module::register()`.

`Offers/` holds the support offers: `OfferRecord` and `OfferRepository` (the table, at the quota lock level), `SupportComponent` (the fee component `support` at the support stage, one `support:<key>` item per applying offer, capped together at the base price), `OfferChangeGuard` (the refusal of a save that would take a line or a refusal from a registration that selected the offer, run by the preview and the save), `SetSupportOffers` (`kalaka/set-support-offers`, which the money settings apply runs; it also declares each offer's consent field, and the answer field of an offer that must be requested) with `OffersInput`, `OfferRequests` (the request source, with its `awaitingRule()` for the admin grid), `OfferSeatPool` and `OfferClaims` (the seats: a claim for every chosen offer, limited or not, and `pools()` for the form host's `seats_left.<offer key>.1`). `Api/` holds `Offers` (an event's offers and `propose()`), `Offer` and `ProposedOffers`.

`Share/` holds the congregation share: `ShareSettings` and `ShareSettingsRepository` (the table: a row means the share is on for the event), `ShareComponent` (the fee component `share` at the share stage: one undivided zero-sum pair of `share` lines, participant -X' and congregation +X', named alike), `SetShare` (`kalaka/set-share`, which the money settings apply runs; it declares the two participant fields `share_mode` and `share_amount`) and `ShareInput` (the check of the two keys by core's `checkDeclarable()`: a form's field of the type is adopted, any other holder refuses). `Api/` holds `Share` (`isOn()` and `propose()`) and `ProposedShare`. The module also declares the payer kind `congregation` (`SharePayerKind`, a `PayerKindSource`).
