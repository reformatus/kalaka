# Registrations

Registrations, field values, submissions, presets, statuses, waitlist, reference codes and derived facts.

At the module root: `Registration` and `RegistrationRepository` (the only writer of `kalaka_registrations`, keyed by event ID and reference code), `RegistrationList` (the registrations of an event with their computed sorszám), `ReferenceCode` (the validity rule), `ReferenceCodeGenerator` and `ReferenceCodeQuery` (issuing a code), `SecretLink` (the secret of a registration's link), `SubmitRegistration` (the use case `kalaka-portal/submit-registration`: capacity, the "full" latch, the waitlist, the reference code, repeated submits) and `RegistrationCount` (the places an event's registrations take). `FieldValue/` holds `FieldValue` and `FieldValueRepository` (the only writer of `kalaka_field_values`, one row per answered field), `Answer/` holds `AnswerRequest` (the use case `kalaka/answer-request`) and `AnswerRepository` (the only writer of `kalaka_answers`, one append-only row per answering act), `Submission/` holds `Submission`, `SubmissionRepository` (the only writer of `kalaka_submissions`, append-only) and `FormSubmissionQuery`.

`Api/` holds `RegistrationKey`, `RegistrationStatus`, `Registrations` (`find()`: a plain read as `RegistrationRead`, never the secret; `firstSubmission()`: the form and form version of the first submission; `values()`: the current field values; `writeValue()`: one field value from the declaring extension's own code, named by its declarer; `lock()`: reads a registration `FOR UPDATE`, so the run holds it; `factsOf()`: its fact source; `openOf()`: an event's `registered` and `waitlisted` registrations), `RegistrationFacts` (the fact source: event values, code, status with its word, `registration.awaits_answer`, submit time), `Requests` (a registration's requests with their latest answer records and the computed `awaits()` read from the sources' answer fields, and `awaitingCondition()`, the same question compiled to SQL from the sources' rules for the admin grid's column), `RequestSource` (the extension point: which requests a registration has, whether each is answered by its answer field, the same as a declarative `AwaitingRule` with its `FieldTest`s and `FieldTestKind`, and writing the answer to the source's own field), `AwaitingRule`, `FieldTest`, `FieldTestKind`, `Request`, `RequestKind`, `RequestState`, `Answer`, `AnswerRead`, `OfferSeats` and `NoOfferSeats` (the seam to the seat rule), `SecretLinks` (the secret link `kalaka_link=<eventId>.<code>.<secret>` and the signed active-registration token: `matches()`, `url()`, `fromLink()`, `activeToken()`, `verifyActiveToken()`), and the submit seam: `RegistrationSubmit` (`submit(SubmitRequest, Actor): SubmitResult`: checks the answers before the transaction, then runs the use case), `SubmitRequest`, `SubmitResult`, `SubmitToken` (the form page's token against repeated submits) and `SubmitTokenReused` (a token spent on other answers) `FormSubmissions` (whether a form has submissions, for Forms' delete and event guards), `Serials` (the sorszám by code, from `RegistrationList`) and `RegistrationTables` (the tables another module may read by name and the sorszám order, which `RegistrationList` uses too; deptrac lets only the admin view query use it). deptrac's "Registration data" layer holds the readers (`Registrations`, `RegistrationRead`, `Serials`, `FormSubmissions`, `SecretLinks`): Admin reaches them only through the view query, and full-access code (`Admin\FullAccess\`) through its own layer.

Tables, created by the schema in `Module.php`: `kalaka_registrations`, `kalaka_field_values`, `kalaka_submissions`, `kalaka_answers`.

`Cli/RegistrationSeeder` contributes sample registrations to `wp kalaka seed`: guests submit the Forms seeder's sample form through `RegistrationSubmit`, so the event fills up and the last ones are waitlisted.

Entry points: `wp kalaka seed` (`Cli/RegistrationSeeder`); the form page (S12) calls `Api\RegistrationSubmit`.
