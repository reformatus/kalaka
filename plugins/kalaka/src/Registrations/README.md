# Registrations

Registrations, field values, submissions, presets, statuses, waitlist, reference codes and derived facts.

At the module root: `Registration` and `RegistrationRepository` (the only writer of `kalaka_registrations`, keyed by event ID and reference code), `RegistrationList` (the registrations of an event with their computed sorszám), `ReferenceCode` (the validity rule), `ReferenceCodeGenerator` and `ReferenceCodeQuery` (issuing a code), `SecretLink` (the secret of a registration's link), `SubmitRegistration` (the use case `kalaka-portal/submit-registration`: capacity, the "full" latch, the waitlist, the reference code, repeated submits) and `RegistrationCount` (the places an event's registrations take). `FieldValue/` holds `FieldValue` and `FieldValueRepository` (the only writer of `kalaka_field_values`, one row per answered field), `Answer/` holds `AnswerRequest` (the use case `kalaka/answer-request`) and `AnswerRepository` (the only writer of `kalaka_answers`, one append-only row per answering act), `Submission/` holds `Submission`, `SubmissionRepository` (the only writer of `kalaka_submissions`, append-only) and `FormSubmissionQuery`.

`Status/` holds the four status acts (`AdmitRegistration`, `WithdrawRegistration`, `RemoveRegistration`, `RestoreRegistration`, each a thin class over `StatusChange`: admit from the waitlist, record a withdrawal, remove, restore; `preview` answers what an act would do), `StatusLock` (the one lock-and-recheck of every status act) and `Leaving` (the one copy of the leave and of the money a leaving act would leave, called by the staff acts and by the participant's own withdrawal) and `WithdrawOwnRegistration` (the use case `kalaka-portal/withdraw-registration`: the registrant withdraws their own `registered` or `waitlisted` registration; its preview gives `{allowed, paid, owed_after, retained, surplus}` of their own payer (`retained`: what the event's retention rule keeps of `paid`; `surplus`: the rest, owed back)). `Api/` also holds `StatusAct` (the one table of the acts: action, target, allowed statuses), `StatusActs` (which acts a registration's status allows now), `StatusActions` (runs an act for the command line), `OwnWithdrawal` (runs the participant's own withdrawal as the secret-link actor, for Portal), `StatusActRefused`, `RegisteredBy` (the act that last made a registration `registered`) and `SeatClaims` (the one read of seat claims). `Api/` holds `RegistrationKey`, `RegistrationStatus`, `Registrations` (`find()`: a plain read as `RegistrationRead`, never the secret; `firstSubmission()`: the form and form version of the first submission; `values()`: the current field values; `writeValue()`: one field value from the declaring extension's own code, named by its declarer; `lock()`: reads a registration `FOR UPDATE`, so the run holds it; `factsOf()`: its fact source; `openOf()`: an event's `registered` and `waitlisted` registrations; `openHolds()`: whether one of them holds a value in a field), `FieldCorrections` and `FieldCorrectionPlan` (a staff correction of a field value: the value's writer and the seats that follow it; `plan()`, `lockPools()`, `lock()`, `check()`, `write()`, `wouldOverfill()` and `move()`; it returns no stored value), `RegistrationFacts` (the fact source: event values, code, status with its word, `registration.awaits_answer`, submit time), `Requests` (a registration's requests with their latest answer records and the computed `awaits()`/`awaitsOf()`, read from the sources' answer fields), `RequestSource` (the extension point: which requests a registration has, whether each is answered by its answer field, and writing the answer to the source's own field), `Request`, `RequestKind`, `RequestState`, `Answer`, `AnswerRead`, `OfferSeats` and `SeatOfferSeats` (the seam to the seat rule, over `Seats`), `SecretLinks` (the secret link `kalaka_link=<eventId>.<code>.<secret>` and the signed active-registration token: `matches()`, `url()`, `fromLink()`, `activeToken()`, `verifyActiveToken()`), and the submit seam: `RegistrationSubmit` (`submit(SubmitRequest, Actor): SubmitResult`: checks the answers before the transaction, then runs the use case), `SubmitRequest`, `SubmitResult`, `SubmitToken` (the form page's token against repeated submits) and `SubmitTokenReused` (a token spent on other answers) `FormSubmissions` (whether a form has submissions, for Forms' delete and event guards), `Serials` (the sorszám by code, from `RegistrationList`) and `RegistrationTables` (the tables another module may read by name and the sorszám order, which `RegistrationList` uses too; deptrac lets only the admin view query use it). deptrac's "Registration data" layer holds the readers (`Registrations`, `RegistrationRead`, `Serials`, `FormSubmissions`, `SecretLinks`): Admin reaches them only through the view query, and full-access code (`Admin\FullAccess\`) through its own layer.

`RegistrationFacts` holds the registration's field values too, typed by `Forms::participantFacts()` (S25).

`Seats/` holds the seat noun: `SeatRecord`, `SeatRepository` (the only writer of `kalaka_seats`), `SeatCount` (the seats held in a pool) and `EventSeatPool` (the event's own pool, whose seats are its `registered` registrations). The seat API in `Api/`: `Seats` (the one seat rule: `held()`, `left()`, `over()`, `holds()`, `wouldOverfill()`, `take()`, `retake()` returning a `SeatOutcome`, `release()`, `releaseAll()`, `lock()` and `inLockOrder()`; a seat is taken only inside an act on a held registration), `SeatPool` (what a module implements for its own limited pool: its identity, lock level and row, limit and `lock()`), `SeatClaim` (a field and the pool a choice in it takes a seat in), `SeatClaimSource` (the contribution point: `claims()` for a submit's answers, `pools()` for every pool the source can claim; a source locks, counts and writes nothing; modules register one with `Contributions::seatClaimSource()`), `PoolEntry` (one of its pools: field key, option value, pool), `SeatOutcome` (`Held`, `Over` or `None`, what `retake()` did), `SeatAct` (why a seat was taken) and `SeatsFull`. `Registrations::refuseRemovingChosen()` throws `ItemChosen` (`kalaka_item_chosen`) when an open registration holds the item (a tier, an option, an offer) a save would remove; a module's own guard extends `ItemChosen`. A use case that locks several pools or rows of one level takes them in the order of Foundation's `Api\UseCase\LockOrder::compare()` (`Seats::inLockOrder()` does it for pools).

Tables, created by the schema in `Module.php`: `kalaka_registrations`, `kalaka_field_values`, `kalaka_submissions`, `kalaka_answers`, `kalaka_seats` (one row per held seat; `Api\Seats` is the only writer).

`Cli/RegistrationSeeder` contributes sample registrations to `wp kalaka seed`: guests submit the Forms seeder's sample form through `RegistrationSubmit`, so the event fills up and the last ones are waitlisted.

Entry points: the portal route `kalaka-portal/v1/withdraw` (Portal's `Rest\WithdrawRoute`, through `Api\OwnWithdrawal`); the abilities `kalaka/admit-registration`, `kalaka/withdraw-registration`, `kalaka/remove-registration` and `kalaka/restore-registration`; `wp kalaka registration admit|withdraw|remove|restore` (Admin's command); `wp kalaka seed` (`Cli/RegistrationSeeder`); the form page (S12) calls `Api\RegistrationSubmit`.
