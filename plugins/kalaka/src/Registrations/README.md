# Registrations

Registrations, field values, submissions, presets, statuses, waitlist, reference codes and derived facts.

At the module root: `Registration` and `RegistrationRepository` (the only writer of `kalaka_registrations`, keyed by event ID and reference code), `RegistrationList` (the registrations of an event with their computed sorszám, and `statusesOf()` behind `Registrations::statusesOf()`), `ReferenceCode` (the validity rule), `ReferenceCodeGenerator` and `ReferenceCodeQuery` (issuing a code), `SecretLink` (the secret of a registration's link), `SubmitRegistration` (the use case `kalaka-portal/submit-registration`: the one waitlist read `Seats::left()` of the event's pool, the "full" latch, the seats of the limited choices taken through `Seats` (a waitlisted submit may claim no limited pool), the reference code, repeated submits), `SubmitAdditionalForm` (the use case `kalaka-portal/submit-additional-form`: an additional form's supplementary submission to an existing registration, S60) and `RegistrationCount` (the `registered` registrations of an event: the seats held in the event's own pool, read by `Seats::held()`). `FieldValue/` holds `FieldValue` and `FieldValueRepository` (the only writer of `kalaka_field_values`, one row per answered field), `Answer/` holds `AnswerRequest` (the use case `kalaka/answer-request`) and `AnswerRepository` (the only writer of `kalaka_answers`, one append-only row per answering act), `Submission/` holds `Submission`, `SubmissionRepository` (the only writer of `kalaka_submissions`, append-only) and `FormSubmissionQuery`. Drafts (S74): `Draft/` holds `Draft` and `DraftRepository` (the only writer of `kalaka_drafts`), the use cases `SaveDraft`, `HandOverPrefill`, `SettleHandoff`, `ClaimDraft`, `ResolveDraftClaim`, `ResolveGuestHandoff` and `SweepDrafts`, `DraftChoice` (what a choice does to the draft that stays) and the periodic step `DraftSweep`.

`Status/` holds the four status acts (`AdmitRegistration`, `WithdrawRegistration`, `RemoveRegistration`, `RestoreRegistration`, each a thin class over `StatusChange`: admit from the waitlist, record a withdrawal, remove, restore; `preview` answers what an act would do). `Api/` also holds `StatusAct` (the one table of the acts: action, target, allowed statuses), `StatusActs` (which acts a registration's status allows now), `StatusActions` (runs an act for the command line), `StatusActRefused`, `RegisteredBy` (the act that last made a registration `registered`) and `SeatClaims` (the one read of seat claims). `Api/` holds `RegistrationKey`, `RegistrationStatus` (`showsDetails()`: the one read of what a waitlisted registrant sees, not an action gate), `Registrations` (`find()`: a plain read as `RegistrationRead`, never the secret; `firstSubmission()`: the form and form version of the first submission; `values()`: the current field values, also the prefill of an additional form; `writeValue()`: one field value from the declaring extension's own code, named by its declarer; `lock()`: reads a registration `FOR UPDATE`, so the run holds it; `factsOf()`: its fact source; `openOf()`: an event's `registered` and `waitlisted` registrations; `leftOf()`: its `withdrawn` and `removed` ones; `openHolds()`: whether one of them holds a value in a field; `openChose()`: whether one of them holds a positive number in it; `statusesOf()`: the statuses of an event's given codes, one read), `FieldCorrections` and `FieldCorrectionPlan` (a staff correction of a field value: the value's writer and the seats that follow it; `plan()`, `lockPools()`, `lock()`, `check()`, `write()`, `wouldOverfill()` and `move()`; it returns no stored value), `RegistrationFacts` (the fact source: event values, the registration's field values by participant-field key, code, status with its word, `registration.awaits_answer`, the time it last became registered, the last changed answer, and `paymentDue()`: the one due date every caller reads; `formTypes()`, `formValues()` and `formRead()`: the `registration.*` keys an additional form's conditions read, and their comparable text), `Requests` (a registration's requests with their latest answer records and the computed `awaits()` (true, false, or null for a registration that is not `registered`: N/A) read from the sources' answer fields, and `awaitingCondition()`, the same question compiled to SQL from the sources' rules for the admin grid's column), `RequestSource` (the extension point: which requests a registration has, whether each is answered by its answer field, the same as a declarative `AwaitingRule` with its `FieldTest`s and `FieldTestKind`, and writing the answer to the source's own field), `AwaitingRule`, `FieldTest`, `FieldTestKind`, `Request`, `RequestKind`, `RequestState`, `Answer`, `AnswerRead`, `SecretLinks` (the secret link `kalaka_link=<eventId>.<code>.<secret>` and the signed active-registration token: `matches()`, `url()`, `fromLink()`, `activeToken()`, `verifyActiveToken()`), and the submit seam: `RegistrationSubmit` (`submit(SubmitRequest, Actor): SubmitResult`: checks the answers before the transaction, then runs the use case, `SubmitAdditionalForm` when the request names a target registration), `SubmitRequest`, `SubmitResult`, `SubmitToken` (the form page's token against repeated submits) and `SubmitTokenReused` (a token spent on other answers) `FormSubmissions` (whether a form has submissions, for Forms' delete and event guards), `Serials` (the sorszám by code, from `RegistrationList`) and `RegistrationTables` (the tables another module may read by name and the sorszám order, which `RegistrationList` uses too; deptrac lets only the admin view query use it). deptrac's "Registration data" layer holds the readers (`Registrations`, `RegistrationRead`, `Serials`, `FormSubmissions`, `SecretLinks`): Admin reaches them only through the view query, and full-access code (`Admin\FullAccess\`) through its own layer. For drafts, `Api/` also holds `Drafts` (what a form opens with, the autosave, the handoff, the claim and the choice), `DraftClaim` (the claim token and its two cookies: the draft's and the waiting handoff's) and `DraftClaimOutcome`, and `RegistrantCookie`, the one cookie policy of a registrant's browser (SB-5), which `DraftClaim` and Portal's active registration both set their cookies through.

`RegistrationFacts` holds the registration's field values too, typed by `Forms::participantValues()` (S25).

Tables, created by the schema in `Module.php`: `kalaka_registrations`, `kalaka_field_values`, `kalaka_submissions`, `kalaka_seats` (one row per held seat; `Api\Seats` is the only writer), `kalaka_answers` (one append-only row per answering act; `Api\AnswerRepository` is the only writer), `kalaka_drafts` (S74: `Api\Drafts` is the only writer).

`Cli/RegistrationSeeder` contributes sample registrations to `wp kalaka seed`: guests submit the Forms seeder's sample form through `RegistrationSubmit`, so the event fills up and the last ones are waitlisted.

Entry points: the abilities `kalaka/admit-registration`, `kalaka/withdraw-registration`, `kalaka/remove-registration` and `kalaka/restore-registration`; `wp kalaka registration admit|withdraw|remove|restore` (Admin's command); `wp kalaka seed` (`Cli/RegistrationSeeder`); the periodic run (`Draft\DraftSweep`, contributed in `Module.php`); the form page (S12) calls `Api\RegistrationSubmit`. Forms' form page reaches the module only through `Api`: the submit (`Api\RegistrationSubmit`, from the submit route) and drafts (`Api\Drafts`, from `Forms\EventFormHost`, which the form page, the draft and claim routes and `Forms\DraftHandoff` on `wp` use).
