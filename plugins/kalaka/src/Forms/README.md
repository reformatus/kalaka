# Forms

Forms, the registration slot, field types, field definitions, values and conditions, prefill and form links.

A form is a `kalaka_form` post (registered in `Module.php` with its settings as post meta: `kalaka_event_id`, `kalaka_placement` and `kalaka_required_role`; the password is the post password). Its content is the definition, block markup built from the field blocks. Forms are built in the block editor, by full access only: the post type has `show_ui` and `show_in_rest` but no menu item, and `FormRestController` refuses every REST read without `kalaka_full_access`; the settings are in REST for the same users. A form's version is the ID of its latest revision that is not an autosave; WordPress saves none on insert, so `FormPosts::ensureRevision()` saves the first one, and revisions of forms are never pruned.

On every save (`wp_insert_post_data`), `FieldKeys` sets each field's missing key from its title and each choice option's missing value from its label, with `KeyDerivation`; a derived key avoids every key the form's event ever had (`kalaka_participant_fields`), and a block that arrives without a key first takes back the key of the stored field of its type and title that no incoming block holds (the editor does not re-read the keys the server set). `FormEvent` tells a save which event the form has: the one the REST request or `meta_input` sets, else the stored one; once a form has fields its event is fixed, and the meta filters refuse a change on any path. Then `DefinitionCheck` refuses a change of the event of a form with fields (`event_fixed`) and runs `ParticipantField\SharedKeyCheck` on every save but an autosave (a key twice in the form, `duplicate_key`; a shared key of another type, `type_clash`; a `system` field's key, `system_field`; an `extension` field's key unless the extension declared it form-writable, `extension_field`; an option an `extension` field's declarer did not declare, `extension_option`; decimals other than an `extension` field's declared ones, `extension_decimals`), and the live form's definition check on a form saved as published or scheduled (and again on `publish_future_post`, before WordPress publishes a scheduled form: a broken one goes back to draft and its author gets the notice): the REST save is refused with a 400 (`rest_pre_insert_kalaka_form`), and any other save path (code, WP-CLI, a revision restore) is vetoed gracefully in the filter (a published form keeps its stored content, any other form stays unpublished) with an admin notice for the saving user, a log line, and on WP-CLI a warning and a failing exit; nothing throws out of a core filter. `BrokenForms` keeps the list of published forms whose definition is broken (saved before the check, or written around it) in a non-autoloaded option, recomputed when a form changes, and `BrokenFormsWarning` shows it as a site warning; such a form stays closed.

`BlockGate` (on `allowed_block_types_all`) gates the blocks by post type: a `kalaka_form` editor gets an allow-list (the field types' blocks, `FORM_ONLY_BLOCKS`, `CONDITION_BLOCKS` and `FORM_CORE_BLOCKS`), and any other editor gets the gated blocks (the field types' blocks and `FORM_ONLY_BLOCKS`) only when a `BlockHost` names them: an incoming list is narrowed, an allow-all `true` stays `true` and the editor script unregisters the gated blocks on the client (`Blocks/form/hidden.js`, from the names `Engine\BlockGate::hiddenHere()` gives `Module::editorScriptData()`, sent as `hidden` in `window.kalakaFormEditor`). The condition blocks are not gated: every editor offers them. There is no `ancestor`.

Once the post and its settings are stored (`wp_after_insert_post`, which a trash and a restore fire too), or once a form
is deleted for good (`before_delete_post` keeps its event, `deleted_post` syncs), `ParticipantFieldSync` reads the
fields of every form of the event that is not trashed (`ParticipantField\FieldBlocks`) and declares them through
`ParticipantFields\Api\ParticipantFields::declare()` (the use case `DeclareParticipantFields` of the `ParticipantFields`
module), as the saving user: it declares new keys (the field's title and option labels are the ones it is first declared
with, and stay the field's own), unions choice options by value (an `extension` field's options are its declarer's) and
retires the fields and options no form holds any more. A form field that clashes with the event's field (only a form
written around the save check) is left out and logged, and the rest is declared; `Forms::definition()` refuses the
current version of such a form (`type_clash`, `system_field`, `extension_field`, `extension_option`), so a published one
is closed and listed by `BrokenForms`. Fields are listed in the order they were declared (`position`).
`Forms::participantFields()` is `ParticipantFields::of()` with, per field, the forms of the event that hold it now
(`ParticipantField::withForms()`). The table, its records and its use cases belong to the `ParticipantFields` module;
`ParticipantField/` here holds `FieldBlocks` and `SharedKeyCheck`, which read the event's fields through
`ParticipantFields::of()`, retired ones included. `ParticipantFields::rename()` (`RenameParticipantField`) is the only
change of a field's title or option labels after they are declared, for a `form` or `staff` field;
`ParticipantFieldsRoute` serves it as `PATCH kalaka-admin/v1/events/{id}/participant-fields/{key}` with `{title?,
options?}`, for the form editor's "update the field's text too?" and the field list.

The form engine is `Engine/` (`Kalaka\Forms\Engine`): everything that reads, walks, checks and renders a form without knowing what it belongs to. Its contract is the `Api/` types other than `Forms`, `EventValues` and `AfterSubmit`, which stay at their names; deptrac's `Forms Engine` and `Forms Engine Api` layers let it use only Foundation Api, its own Api, WordPress and the bundled brick/math, never Events, Registrations, ParticipantFields, Admin or the rest of Forms. What it needs about the form's owner it asks one host, `Api\FormHost`: the facts a condition reads and their types (`factTypes($form)`, `facts()`, null when the owner is gone), the access refusals and the window (`refusals()`, `window()`), the problem of the current version's keys against the keys beyond the form (`keyProblem()`), the stored values the form opens with (`prefill()`), the person's draft (`draft()`, `saveDraft()`, `resolveDraftClaim()`; S74), the submit token and the submit (`submitToken()`, `submit()`), and the after-submit section's keys (`afterSubmitTypes()`). `EventFormHost`, at the root, is Kaláka's event form, the first host: its facts and their types (`typesOf()` and `factsFor()`: `EventValues`, the form-only places left of the event and of every pool a seat claim source lists, and custom points, and an additional form's `registration.*` facts and stored values), the event's refusals (`refusalsOf()`, which `Forms::refusals()` is, with an additional form's open period through `OpenPeriod`; `refusals()` adds an additional form's registration: the active one of the event, `registered`; any other is refused as `RegistrationMayNotSubmit`, so its form shows closed), an additional form's target and prefill (the active registration, `Portal\Api\ActiveRegistration`, and its field values, `Registrations\Api\Registrations::values()`), `ParticipantField\SharedKeyCheck`, `Registrations\Api\SubmitToken` and `RegistrationSubmit`, and `AfterSubmit::TYPES`. `Api\Forms` keeps its methods and hands them to `Engine\FormEngine` with an `EventFormHost`; `Module.php` and `Blocks/form/render.php` give the form page and its routes the same host.

In `Engine/`: `FormEngine` (the reads and checks of a form for a host: `form()`, `definition()` with the host's key problem on the current version, `latestDefinition()`, `blocks()`, `afterSubmit()`, `validate()`, `availability()`), `FormPosts` (reads the posts, their revisions and their settings), `DefinitionParser` (reads the field blocks, in document order, out of any core blocks and condition branches around them, numbers the chains and collects the triggers; the host's keys are what conditions may read; and refuses a typed placeholder the part it sits in cannot fill, `unknownPlaceholders()`, N1182), `SlotRules` (the registration slot's markings, none of them inside a condition branch, and the fields an extension requires, `Api\SlotRequirement`), `FormWalk` with `FormFacts` and `FormWalkResult` (the one walk of a form over answers: what shows, which branch of each chain holds, which options are offered, the valid answers and the errors), `AnswerValidator` (the server's check of answers: the walk, then any error refuses them), `BlockGate`, `FieldMarkup` (the field blocks' shared markup), `PageMarkup`, `BranchMarkup`, `ThemeAdapters` (picks the theme adapter once per request), and the form page (`FormPage`, `FormPageView`, `ChoiceParts`, `SubmitGuard`, `SubmitAttempt`, `Rest/FormRoutes`). At the root: `EventFormHost`, `OpenPeriod` (an additional form's open period: two date references, a fixed UTC instant or an event point, in the settings `kalaka_opens` and `kalaka_closes`), `DraftHandoff` (S74: on `wp`, a `kalaka[<key>]` prefill becomes a guest draft with a 303, and a logged-in visitor claims the cookie's guest draft), `DefinitionCheck` (the save check), `PageCheck` (an ordinary post's or page's typed placeholders, refused on save, `kalaka_unknown_placeholder`, N1180), `FormDeletion` (a form with submissions is never deleted permanently), `BrokenForms` and `BrokenFormsWarning`, `FieldKeys` (keys and option values), `FormEvent`, `ParticipantFieldSync`, `ParticipantFieldsRoute`, `FieldBlockCheck` and `FormRestController`.

`Api/` holds `Forms` (the facade, with `CONSENT_FIELD`, the consent's field type key, for readers outside Forms: `form()`, `definition()`, `latestDefinition()`, `blocks()`, `refusals()`, `validate()`, `availability()`, `participantFields()`, `participantValues()`: the values of a registration's stored answers over the event's participant fields, `participantFieldValues()`: the same fields, each with its value, `withoutAccountBlock()` and `refreshBrokenList()`: what a change of the event's account mode reads before and does after, `Events\Api\Events::update()`), `Form`, `FormPlacement`, `FormDefinition`, `FormField`, `FormBranch`, `FormChain`, `FormAvailability` (what a form shows for its answers, the front end's read model), `AccessRefusal`, `AfterSubmit` (the after-submit section's block and its value keys), `PageDefinition` (a page of a multi-page form), `FormTerminal` (a submit while a terminal page shows), `FormOutdated` (a page built from a version that is no longer the latest), `FormRefused` (a form that cannot be used now, with the refusal codes), `FormCaching` (a page that places a form is never cached), `ValidatedAnswers`, `InvalidAnswers`, the fact source `Facts`, the event keys (`EventValues`), the value API (`Values`, the facade with `render()` and `check()`, `Value`, `ValueType` and `ValueContext`) and the field-type point: `FieldType`, `AbstractFieldType` (with `settings()`, the block's settings the event's participant field keeps), `FieldTypeInput`, `FieldAnswer` and the optional `MoneyRelevantFieldType`, `OptionsFieldType` (the block holds options as a choice does: their values derived on save and checked) and `PathFieldType` (a marker: the field's value is a path, which a condition reads with `contains`, never `equals`; `Forms::pathKeys()` lists the event's such keys), with `FieldMarkup`, the shared field markup (the wrapper, the classes of each element role with the theme adapter's, the required marker and the error element, and the answer the field opens with, `prefilled()`) that an extension's field block renders with, as `Engine\FieldMarkup` gives the core blocks. For drafts (S74): `AnswerSet` (the answers by field key, the shape a submission keeps and a draft holds), `FormDraft` (what a form opens with from its host's draft: the answers, the autosave, the claim waiting for the person's choice, its count and notice) and `DraftClaimChoice` (merge, keep_draft or keep_link). Field types are contributed with `Contributions::fieldType()`. The theme-adapter point: `ThemeAdapter`, `ThemeAdapterInput`, `ThemeAdaptation`, `ElementRole` and `FieldWrapper`, contributed with `Contributions::themeAdapter()`. `BlockHost`, a declaration contributed with `Contributions::blockHost()`.

`Forms::participantValues()` reads no post, only `ParticipantFields::of()` (its table and the block registry), so
the evaluation calls it inside the transaction (S25).

`Engine/FieldType/` holds the nine core types: `NameFieldType`, `EmailFieldType`, `PhoneFieldType`, `DateFieldType`, `TextFieldType`, `ChoiceFieldType`, `ConsentFieldType` and `ScaleFieldType` (a point from `min` to `max`, 1 to 5 by default and 2 to 11 points, with an optional label per point in `pointLabels`; stored as the integer, a number value whose text is the number and the point's label, `5 – inkább egyetértek`; `ScaleFieldType::range()` is the one check of its settings, and `DefinitionParser` refuses a form with an invalid one, `invalid_scale`), and `NumberFieldType` (a whole or decimal number with `min`, a `step` counted from the minimum, `max`, a decimals count and a prefix/suffix; its text groups digits with no-break spaces and writes a negative with U+2212; `readSettings()` is the one check, and `DefinitionParser` refuses `invalid_number`; its settings are kept on the participant field). `Blocks/<type>-field/` holds each type's `block.json` (title, the `kalaka` category, no `ancestor`), `render.php` (through `FieldMarkup`) and `edit.js` (the scale's range logic in `range.js`). Every block is registered from `build/` (`npm run build` builds and copies the block files there), by `Module::register()`. The editor is one script, `Blocks/form/index.js` (handle `kalaka-form-editor-script`, which every Kaláka block's `block.json` names): it registers each block's `edit.js`, keeps field keys and option values stable (`Blocks/form/keys.js`), reads the field-type blocks, the condition keys and a date reference's bounds and the field-type blocks that are paths (`pathFieldTypes`) from the server (`Blocks/form/server.js`, printed by `Module::editorScriptData()`), and imports the structural CSS (`Blocks/form/style.css`, the form block's `style`). It sets `window.kalakaFieldEditor`, the field-editor pieces of `Blocks/form/field.js` and `participant-ui.js` (`FieldInspector`, `FieldTitle`, `preview`, `REQUIRED`, `useFieldCanvas`, `useStableKey`), the one way an extension's field block reaches them; that block's `editorScript` names `kalaka-form-editor-script` before its own script.

`Engine/Condition/` holds the stored condition format: `ConditionParser` reads it into a `Condition` (made of `Comparison`s, `DateReference`s, `Operator`s and `MatchMode`s) for the keys a `ConditionScope` allows (`FormScope` in a form, `ContextScope` over a fact source anywhere else, `DeclaredScope` over declared keys when a condition is saved), `ConditionEvaluator` decides whether it holds (pure; the one evaluator), `Chains` finds the `kalaka/if`, `kalaka/else-if` and `kalaka/else` chains among sibling blocks, and `ChainMarks` numbers them once on the parsed blocks (chain number and branch index as block attributes), for the definition and the rendered page alike.

`Engine/Value/` holds the renderer behind `Values::render()` (a mail body; the first failure stops it) and `Values::renderPage()` (an ordinary page, whose context is the visitor's active registration and its event; a failing chain, binding or inline value renders nothing and is logged, and a typed `{{key}}` the context does not declare fails the page, N1150): `ChainPass` keeps the held branch of every chain, `BindingSource` is the Block Bindings source `kalaka/value`, `Placeholders` fills the placeholders typed as `{{key}}` in text and attributes with the HTML API (and is the one finder the save check and `placedKeys()` use), `InlineValues` fills `<span data-kalaka-value="key">` with it, and `RenderStack` holds the context of the render in progress. `DocumentCheck`, behind `Values::check()`, checks a document (a mail body) at save against the keys its context will declare: every chain and condition in every branch, every binding, inline value and typed placeholder. `Blocks/after-submit/` holds the after-submit section, which renders nothing where it sits. `Blocks/form-page/` holds the page block, rendered by `PageMarkup` (a hidden wrapper with its number, a terminal mark and its title) in a form page and nothing elsewhere. Both have an `edit.js` that the form editor registers. `Blocks/if/`, `Blocks/else-if/` and `Blocks/else/` hold the three branch blocks; through `BranchMarkup` they render their inner blocks, with no wrapper, only for the held branch inside those calls; in a form page's marked blocks (`Forms::blocks()`) every branch of a chain that reads only the form's own answers, each in a hidden wrapper with `data-kalaka-chain` and `data-kalaka-branch`, and of any other chain only its held branch (`FormDefinition::withheldChains()`, `ChainMarks::prune()`); nothing anywhere else. Nothing reads the active registration yet, so no page calls `renderPage()` with a context: the slice that adds `ActiveRegistration::current()` wires it.

`Api\Forms` reads WordPress posts, so it runs before or after a use case's transaction, never inside it.

The form page: `Blocks/form/` is the embed block `kalaka/form` (`block.json`, `render.php` with its texts, the script module `view.js` with `answers.js`, the reader of a field's controls, and `view.css`, the loading state, the error colour of field messages and the required asterisk, a field's `label` that names a control (`for`), an extension's too, on its own line above it, a rule that keeps a hidden Vissza, Tovább or Küldés button hidden where a theme gives buttons a `display` of their own (Divi's `.et_pb_button`), and the neutral base of Kaláka's own controls in the `kalaka` cascade layer (`:where()` selectors, inherited fonts and colours, faded borders, the documented `--kalaka-…` properties listed in the file), registered from `src/` as the handle `kalaka-form-view`). The form's Vissza, Tovább and Küldés carry `wp-element-button` beside the adapter's submit-button classes. The shortcode `[kalaka_form id="…"]` (`Module::shortcode()`) renders the same block; both call `Api\FormCaching::preventCaching()`. `FormPage` decides whether the form shows (the load state first, then the form, the host's facts, `FormHost::refusals()`, the definition) and renders the marked blocks of `FormEngine::blocks()` for the host's stored answers (`FormHost::prefill()`, each through its type's `prefill()`; none for a new registration) from `FormEngine::availability()` (S76), inside one `Boundary::render()`: the branch of each chain that shows is unhidden, the controls of a field that does not show are disabled, a choice field renders only its offered options, the host's facts (for an event form the event values, `Api/EventValues`, the one place that declares the event keys) fill the bindings and inline values, and a field block of an extension without the error element (`FieldMarkup::errorElement()`) gets one, and each field block renders the answer it opens with (`FieldMarkup::withPrefill()` around the render, `FieldMarkup::prefilled()` in the block). A field block whose `label`, or whose choice option's `label`, the form leaves empty shows the participant field's text: `FormEngine` fills the content (`Engine/LabelFallback`, only when a label is empty) from `FormHost::labelFallbacks()` before the blocks are rendered and the definition is parsed, so a form's own labels are never replaced. The form carries the theme adapter's form classes and error colour (`--kalaka-error-color`) and its buttons the adapter's submit-button classes. The script re-fetches through the re-fetch route and sends through the submit route of `Engine\Rest\FormRoutes` (see the entry points). `FormPageView` is the page's result: one refusal or the content and the form element's context (the URLs, the version, the failure text, `nonce`, the triggers and the pages). `nonce` is `wp_create_nonce('wp_rest')` for a logged-in person and empty for a guest; the script sends it as `X-WP-Nonce` on the re-fetch and the submit, so the routes see the account. The script (`view.js`) holds no condition: on a change of a trigger it re-fetches and applies the answer (the chains' branches, the fields' disabled controls, the re-rendered choice fields with the remembered ticks, the pages that show); on a multi-page form it shows the current page, checks it with a re-fetch that sends `page` on Tovább, moves back on Vissza and on the browser's Back button (`history.pushState`, scoped to the form), and after a refused submit goes to the earliest page with an error or to the terminal page that shows. While a re-fetch, a page check or a send runs the form is `aria-busy` (dimmed) and its buttons `aria-disabled`, and after 2 seconds the spinner shows; after a failed re-fetch the form is out of date, and Tovább or Küldés re-runs the re-fetch. Only Kaláka's own errors (a `kalaka_` code or messages of fields) show their message; a field's message goes into its error element, which describes its controls (`aria-describedby`, `aria-invalid`); a field's controls dispatch a bubbling `input` or `change` event inside its `[data-kalaka-field]` wrapper, which is how the script clears that field's message on an edit (an extension needs no other contract), and the focus moves to the first field with a message, the message area, the page's title or the after-submit content. `Api\DateText` makes the text of a day (`2026. november 30.`), for the status block too. `FieldBlockCheck` closes the site, through `LoadState::close()`, when a published form holds a `kalaka/` block that is not registered. `Cli/FormSeeder` seeds the sample form (with a field of each kind the admin grid sums) and the page that embeds it, both marked with the meta `_kalaka_seed_sample` (`FormSeeder::MARKER`); after `wp kalaka seed --drop` (`Seeding::dropped()`) it first deletes the marked ones an earlier seed wrote (dev only).

Entry points: `init` (`Module::register()`), `wp_loaded` (`FieldBlockCheck::run()`), `ParticipantFieldsRoute`, `GET kalaka-admin/v1/events/{id}/participant-fields` for the form editor (full access only, `include_retired` to add the retired fields), the block `kalaka/form`, `wp kalaka seed` (`Cli/FormSeeder`); the form page's routes in `Engine\Rest\FormRoutes`, registered on `rest_api_init` through `Boundary::route()`. `POST kalaka-portal/v1/forms/{id}/availability` `{version, answers, page?}` answers `{availability: FormAvailability::toArray(), parts: {key: html}}`, where `parts` are the choice fields with option conditions re-rendered for the answers (`ChoiceParts`); it applies the form's refusals (`FormRefused`) and reads only. `POST kalaka-portal/v1/forms/{id}/submit` `{version, answers, token}` runs `SubmitGuard` (spam protection, S14: a rate limit per account or address, `RateLimiter` and `ClientAddress`; over it `RateLimited`, 429 `kalaka_rate_limited` with `Retry-After`; the `wp-config.php` constant `KALAKA_TRUSTED_PROXIES` names reverse proxies whose `X-Forwarded-For` is trusted) and the host's submit (`FormHost::submit()`; for an event form `RegistrationSubmit::submit()`) as the logged-in user (`AccountActor`, with their roles) or a guest, and answers `SubmitResult::toArray()`. Two more for drafts (S74): `POST kalaka-portal/v1/forms/{id}/draft` `{version, answers, page, claims}` answers `{saved: true}`, the autosave of a person's draft, or a guest's guest draft, whose cookie the first save sets (`FormHost::saveDraft()`; a guest's save that creates the draft counts as a handoff for the rate limit; at most `FormRoutes::DRAFT_LIMIT` bytes, the form's own keys only; a save from before a claim that changed the draft is `kalaka_version_conflict`, 409), and `POST kalaka-portal/v1/forms/{id}/draft/claim` `{choice}` answers `{resolved: true}`, the person's choice between a link's answers and their draft (`FormHost::resolveDraftClaim()`; for an event form a claim that cannot be applied is `kalaka_draft_claim_refused`, 409). `FormRoutes::noStore()` on `rest_request_after_callbacks` sets `Cache-Control: no-store` on every answer of all four. On `wp`, `DraftHandoff`: a `kalaka[<key>]` prefill becomes a guest draft with an uncached 303, and a logged-in visitor's cookie claims its guest draft. The claim popup, `Blocks/form/claim.js` (a `@wordpress/components` Modal, built by the root `webpack.config.js` and registered as `Module::CLAIM_SCRIPT`), which `render.php` enqueues only while the page's context carries `draftClaimUrl`; its texts are `Engine\DraftClaimTexts`.

S44 request fields: a field type that is an `Api\RequestFieldType` (the module ranking) names an assignment set, or, with no set named, holds its own options (`requestSet()` null).
`DefinitionParser` fills its options from `FormHost::requestOptions()` (`Api\RequestOptions`), and
`FormEngine::blocks()` renders it with them. `ParticipantField\SharedKeyCheck`
refuses a request field naming a set the event does not have (`unknown_set`) or a set that has another request field
(`request_field_taken`), and `ParticipantFieldSync` ties each set to its field. Key derivation is `Api\KeyDerivation`,
which Assignments uses too.
