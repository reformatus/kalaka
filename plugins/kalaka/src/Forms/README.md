# Forms

Forms, the registration slot, the event's participant fields, field types, field definitions, values and conditions, prefill and form links.

A form is a `kalaka_form` post (registered in `Module.php` with its settings as post meta: `kalaka_event_id`, `kalaka_placement` and `kalaka_required_role`; the password is the post password). Its content is the definition, block markup built from the field blocks. Forms are built in the block editor, by full access only: the post type has `show_ui` and `show_in_rest` but no menu item, and `FormRestController` refuses every REST read without `kalaka_full_access`; the settings are in REST for the same users. A form's version is the ID of its latest revision that is not an autosave; WordPress saves none on insert, so `FormPosts::ensureRevision()` saves the first one, and revisions of forms are never pruned.

On every save (`wp_insert_post_data`), `FieldKeys` sets each field's missing key from its title and each choice option's missing value from its label, with `KeyDerivation`; a derived key avoids every key the form's event ever had (`kalaka_participant_fields`), and a block that arrives without a key first takes back the key of the stored field of its type and title that no incoming block holds (the editor does not re-read the keys the server set). `FormEvent` tells a save which event the form has: the one the REST request or `meta_input` sets, else the stored one; once a form has fields its event is fixed, and the meta filters refuse a change on any path. Then `DefinitionCheck` refuses a change of the event of a form with fields (`event_fixed`) and runs `ParticipantField\SharedKeyCheck` on every save but an autosave (a key twice in the form, `duplicate_key`; a shared key of another type, `type_clash`; a `system` field's key, `system_field`; an `extension` field's key unless the extension declared it form-writable, `extension_field`), and the live form's definition check on a form saved as published: the REST save is refused with a 400 (`rest_pre_insert_kalaka_form`), and any other save path (code, WP-CLI, a revision restore) is vetoed gracefully in the filter (a published form keeps its stored content, any other form stays unpublished) with an admin notice for the saving user; nothing throws out of a core filter. `BrokenForms` keeps the list of published forms whose definition is broken (saved before the check, or written around it) in a non-autoloaded option, recomputed when a form changes, and `BrokenFormsWarning` shows it as a site warning; such a form stays closed.

`BlockGate` (on `allowed_block_types_all`) gates the blocks by post type: a `kalaka_form` editor gets an allow-list (the field types' blocks, `FORM_ONLY_BLOCKS` and `FORM_CORE_BLOCKS`), and any other editor gets the gated blocks only when a `BlockHost` names them. There is no `ancestor`.

Once the post and its settings are stored (`wp_after_insert_post`, which a trash and a restore fire too), or once a form is deleted for good (`before_delete_post` keeps its event, `deleted_post` syncs), `ParticipantFieldSync` reads the fields of every form of the event that is not trashed (`ParticipantField\FieldBlocks`) and runs `ParticipantField\DeclareParticipantFields` through the runner, as the saving user: it declares new keys (the field's title and option labels are the ones it is first declared with, and stay the field's own), unions choice options by value and retires the fields and options no form holds any more. A form field that clashes with the event's field (only a form written around the save check) is left out and logged, and the rest is declared; `Forms::definition()` refuses the current version of such a form (`type_clash`, `system_field`, `extension_field`), so a published one is closed and listed by `BrokenForms`. Fields are listed in the order they were declared (`position`). `Forms::participantFields()` names, per field, the forms of the event that hold it now and its type's label (the block type's registered title). `ParticipantField/` also holds `ParticipantFieldRecord`, `ParticipantFieldRepository` (its only writer) and `ParticipantFieldQuery`. The table is the module's schema (`Module::schema()`). `ParticipantField\RenameParticipantField` is the only change of a field's title or option labels after they are declared, for a `form` or `staff` field; `ParticipantFieldsRoute` serves it as `PATCH kalaka-admin/v1/events/{id}/participant-fields/{key}` with `{title?, options?}`, for the form editor's "update the field's text too?" and the field list.

At the root: `FormPosts` (reads the posts, their revisions and their settings), `DefinitionParser` (reads the field blocks, in document order, out of any core blocks and condition branches around them), `SlotRules` (the registration slot's markings, none of them inside a condition branch), `AnswerValidator` (the server's check of answers against a definition, dropping the answers of branches that do not hold), `KeyDerivation` and `FieldKeys` (keys and option values), `DefinitionCheck` (the save check), `BrokenForms` and `BrokenFormsWarning`, `BlockGate`, `FormRestController`, `FieldMarkup` (the field blocks' shared markup) and `ThemeAdapters` (picks the theme adapter once per request).

`Api/` holds `Forms` (the facade: `form()`, `definition()`, `refusals()`, `validate()`, `participantFields()`), `ParticipantField`, `Form`, `FormPlacement`, `FormDefinition`, `FormField`, `FormBranch`, `AccessRefusal`, `ValidatedAnswers`, `InvalidAnswers`, the value API (`Values`, the facade with `render()`, `Value`, `ValueType` and `ValueContext`) and the field-type point: `FieldType`, `AbstractFieldType`, `FieldTypeInput`, `FieldAnswer` and the optional `MoneyRelevantFieldType`. Field types are contributed with `Contributions::fieldType()`. The theme-adapter point: `ThemeAdapter`, `ThemeAdapterInput`, `ThemeAdaptation`, `ElementRole` and `FieldWrapper`, contributed with `Contributions::themeAdapter()`. `BlockHost`, a declaration contributed with `Contributions::blockHost()`.

`FieldType/` holds the seven core types: `NameFieldType`, `EmailFieldType`, `PhoneFieldType`, `DateFieldType`, `TextFieldType`, `ChoiceFieldType` and `ConsentFieldType`. `Blocks/<type>-field/` holds each type's `block.json` (title, the `kalaka` category, no `ancestor`) and `render.php`; the blocks are registered from `src/` until the front end adds the JavaScript build, and their editor scripts come with it.

`Condition/` holds the stored condition format: `ConditionParser` reads it into a `Condition` (made of `Comparison`s, `Operator`s and `MatchMode`s) for the keys a `ConditionScope` allows (`FormScope` in a form, `ContextScope` over a `ValueContext` anywhere else), `ConditionEvaluator` decides whether it holds (pure), and `Chains` finds the `kalaka/if`, `kalaka/else-if` and `kalaka/else` chains among sibling blocks.

`Value/` holds the renderer behind `Values::render()`: `ChainPass` keeps the held branch of every chain, `BindingSource` is the Block Bindings source `kalaka/value`, `InlineValues` fills `<span data-kalaka-value="key">` with the HTML API, and `RenderStack` holds the context of the render in progress. `Blocks/if/`, `Blocks/else-if/` and `Blocks/else/` hold the three branch blocks; they render their inner blocks, with no wrapper, only inside `Values::render()` and nothing anywhere else.

`Api\Forms` reads WordPress posts, so it runs before or after a use case's transaction, never inside it.

Entry points: `ParticipantFieldsRoute`, `GET kalaka-admin/v1/events/{id}/participant-fields` for the form editor (full access only, `include_retired` to add the retired fields); the embed block and the form page come with the front end.
