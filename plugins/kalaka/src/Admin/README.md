# Admin

Views and grants, data grid, detail views, notes, audit and settings.

- `Api/AdminAccess`: the admin side's coarse permission check, which the runner calls before an admin use case begins, and the full-access capability (`AdminAccess::FULL_ACCESS`).
- `Api/Access`: what an actor may reach, for the screens: `isFull()`, `grantedEventIds()`, `heldViews()`, `master()`, `fullView()` (a stored view as full access opens it, without a bound value), each a `HeldView`; `viewOf()` (the view an actor opens by view and grant: the one path of the grid's routes and of a bulk act on the grid's rows), `mayReachAdmin()` (the abilities' and the grid routes' gate) and `mayWrite()` (the fine check of a field change). A `HeldView` carries the counted members of its sum row (`counts()`): the view's own, or the master row's for the master view.
- `Api/ViewQuery`: the one read path for registration data: `columns()`, `count()`, `page()` (a `ViewPage` of `ViewRow`s, sorted and paged), `codesOf()` (the codes of every matching row, unpaged), `contains()`, and `aggregates()` (the grid's sum row: one statement over the whole filtered view, by `AggregateSpec`, whose `AggregateKind` is `rows`, `members`, `yes`, `sum`, `filled` or `average`).
- `Api/GridSelection`: the codes of the rows a bulk act reaches when it names the grid's rows (a view, a grant, the grid's filters and search) instead of listing codes: the grid's held view, `GridNarrowing` and `ViewQuery::codesOf()`; the act's own permission check still runs on the codes.
- `Api/Abilities`: admin use cases as WordPress abilities.
- `Api/RegistrationDetail` and `RegistrationDetailRoute`: the detail read of one registration through views and grants, and its REST route (`GET kalaka-admin/v1/events/{event}/registrations/{code}`); the money block only to the holder of a money action of a grant whose view holds the registration.
- `View/`: `ViewShape` (filter, columns and `counts`, the members the sum row counts per column), `View`, `ViewRepository`, `ViewList` (the event's views; `master()` and `masterCounts()` read its master row), and the use cases `SaveView`, `DeleteView` and `CopyViews` (nested).
  - **The master row:** a `kalaka_views` row with `master` 1 holds only the master view's counts; its name, filter and columns are stored empty. Its `master_event` (the event of a master row, null on every other row, written by `ViewRepository`) has a unique key: at most one master row per event. No use case saves it: the grid's counting is the viewer's own for the session, and `CopyViews` only copies an existing row. `ViewList::ofEvent()` and the tabs never list it; `SaveView`, `DeleteView`, `SaveGrant` and `Access::fullView()` refuse it; `CopyViews` copies it onto the target's master row.
- `Grant/`: `Grant`, `GrantRepository`, `GrantQuery`, and the use cases `SaveGrant`, `DeleteGrant`.
- `Grid/`: the per-event „Jelentkezők” page (S37). `GridPage` adds the menu (until the admin frame is built: one top-level item per event that is not archived and that the user reaches, ordered by start, with the submenu „Jelentkezők”, slug `kalaka-event-{id}-registrations`), renders the page and enqueues the app. `FieldDefinitions` reads each participant field's type, options, value type and whether it is required (in every form it sits in); `GridModel` orders the columns (Kód, Név, Állapot, Szám, then the rest), describes them for the app (a decision column by its kind's declared label, states and marks, else its key and the recorded states), names and keys the tabs (one tab per grant, `g{grant}`; a full-access tab is `v{view}`) and builds the sum row from the field types and the picked members; `ViewsData` is the views list (the stored shape and version; the grid app no longer reads it); `Translations` hands core's translations of DataViews' strings to the app; `Texts` holds the Hungarian text PHP renders.
- `Rest/GridRoutes`: the grid's read routes under `kalaka-admin/v1` (rows with core's paging headers and sums, each with the `grant` of a grant holder's tab; the views list), each through `Boundary::route()`, gated by `Access::mayReachAdmin()`; they read through a view `Access` hands out. The grid app saves no view configuration; the abilities `kalaka/save-view` and `kalaka/delete-view` stay for view editing.
- `app/grid/`: the grid's React app (bundled `@wordpress/dataviews`): the tabs, the „Műveletek” toolbar with „Táblázat másolása”, and the sum row, a second `<tr>` portalled into DataViews' `<thead>`. `format.js` is its pure logic (cells, sums, the copy), tested by Jest. S38: `DetailPanel` (the side panel over the grid, opened from a row: the identifying header and the tabs; it reads the detail route and shows only the parts the read returns), `MoneyTab` (the „Pénzügyek” tab: every line is on one of two sides, the payer table and the „Tételek” list have a „Fizetendő” and a „Befizetett” column, and „Tartozás” is Fizetendő − Befizetett, a negative value reading „(túlfizetés)”) and `RecordDialog` („Tétel rögzítése”: one dialog whose first field is „Típus”, Befizetés, Visszafizetés, Díj and Kedvezmény, only the types `allowedTypes( can )` offers (Befizetés and Visszafizetés from `can.record_money`, Díj from `can.record_charge`, Kedvezmény from `can.record_discount`; the server decides each, the panel keeps no status logic) and none preselected unless exactly one is offered; a Díj or Kedvezmény has a participant-visible title and may be saved „completed immediately”, which also records the matching paid-side line; „Korrekció rögzítése” keeps its own dialog, a direction and a required reason with no method or date; they run `kalaka/record-payment`, `kalaka/record-refund` and `kalaka/record-correction`, and `kalaka/record-charge` and `kalaka/record-discount` (Backend #209's design note §9; never called unless the type is offered), through `api.js`; the one adapter for the server's money lines is the SEAM block of `money.js`), `StatusMark`, and `money.js`, their pure logic (amounts in fillér, „30 000 Ft”, the sign rule, the side of each line, „Tartozás” and its preview, the site time zone's days, the dialog's checks), tested by Jest. S20: the panel header shows the confirmation decision's state when the read has it, and `ManualConfirmation` (under the header, so it is reached without the „Pénzügyek” tab) shows the manual flag (who, when, why) with `ConfirmDialog`, which runs `kalaka/set-manual-confirmation` (with `can.confirm_manually`) or the one `kalaka/unconfirm` (with `can.unconfirm`, on any confirmed registration), a reason required (at most 500 characters); the unconfirm dialog shows the server's `registration.unconfirm_warning` first when it is not null, and after the act the panel re-reads the detail and the snackbar follows the re-read; `confirmation.js` is its pure logic.
- `Mail/`: the mail screens (a prototype): `MailPages` adds the site's „Kaláka › Levelezés” page (the sender: pause, budget, each event's queue) and the event's „Levelek” page (a submenu item of the event's own menu item: the action mails, the bodies, the troubled deliveries and the manual mail's batches), full access only, each an empty container plus a configuration (`window.kalakaMail`) for the app; `Texts` holds the Hungarian text PHP renders.
- `app/mail/`: the mail pages' React app (bundled `@wordpress/dataviews`, entry `index.js`, `EventPage` and `SenderPage`). It shows only what the mail reads under `kalaka-admin/v1` return and decides no access; every change is an ability call, and the page reads again after it. `bulk.js` and `ManualMailDialog.js` are the grid's bulk action „Levél küldése”: `GridPage` tells each tab whether it carries `ManualMails::GRANT_ACTION` (full access always), the action sends the ticked rows' codes as a `{ codes }` selection to the manual mail's preview and to `kalaka/send-manual-mail`, which decide again on every call; `manual.js` keys a send so a retry is the same request. `format.js` is the pure logic, tested by Jest.
- `Cli/AdminSeeder`: the seed's view with a parameter and its grant holder (`kalaka_partner`).
- `FullAccess/`: the use cases `GrantFullAccess` and `RevokeFullAccess`, both through `FullAccessChange` (the checks, the audit of the real old value, the capability written per user after the commit); `FullAccessQuery` (the one holder rule: a user's own capability or a role carrying it, read from `usermeta`); `FullAccessOnActivation`, which runs the grant as the system for the activating user only while nobody holds full access; the profile checkbox (`ProfileField`), the Users column (`UsersColumn`), and their Hungarian `Texts`. deptrac names this folder the "Full access" layer: besides the view query, the only Admin code that may use Registrations' readers.

Entry points: the abilities (`kalaka/save-view`, `kalaka/delete-view`, `kalaka/save-grant`, `kalaka/delete-grant`, `kalaka/grant-full-access`, `kalaka/revoke-full-access`), the profile and user-edit screens, the Users list, the per-event „Jelentkezők” page and its `kalaka-admin/v1` routes, the mail pages (`Mail/MailPages`), the registration detail route, WP-CLI `wp kalaka full-access grant|revoke <user>` (`Cli/FullAccessCommand`), and the plugin's activation hook (`FullAccessOnActivation`).
