# Admin

Views and grants, data grid, detail views, notes, audit and settings.

- `Api/AdminAccess`: the admin side's coarse permission check, which the runner calls before an admin use case begins, and the full-access capability (`AdminAccess::FULL_ACCESS`).
- `Api/Access`: what an actor may reach, for the screens: `isFull()`, `grantedEventIds()`, `heldViews()`, `master()`, `fullView()` (a stored view as full access opens it, without a bound value), each a `HeldView`; `mayReachAdmin()` (the abilities' and the grid routes' gate) and `mayWrite()` (the fine check of a field change). A `HeldView` carries the counted members of its sum row (`counts()`): the view's own, or the master row's for the master view.
- `Api/ViewQuery`: the one read path for registration data: `columns()`, `count()`, `page()` (a `ViewPage` of `ViewRow`s, sorted and paged), `contains()`, and `aggregates()` (the grid's sum row: one statement over the whole filtered view, by `AggregateSpec`, whose `AggregateKind` is `rows`, `members`, `yes`, `sum`, `filled` or `average`).
- `Api/Abilities`: admin use cases as WordPress abilities.
- `Api/RegistrationDetail` and `RegistrationDetailRoute`: the detail read of one registration through views and grants, and its REST route (`GET kalaka-admin/v1/events/{event}/registrations/{code}`); the money block only to the holder of a money action of a grant whose view holds the registration.
- `View/`: `ViewShape` (filter, columns and `counts`, the members the sum row counts per column), `View`, `ViewRepository`, `ViewList` (the event's views; `master()` and `masterCounts()` read its master row), and the use cases `SaveView`, `DeleteView`, `CopyViews` (nested) and `SaveMasterCounts`.
  - **The master row:** a `kalaka_views` row with `master` 1 holds only the master view's counts; its name, filter and columns are stored empty. Its `master_event` (the event of a master row, null on every other row, written by `ViewRepository`) has a unique key: at most one master row per event. `SaveMasterCounts` inserts it on the first save. `ViewList::ofEvent()` and the tabs never list it; `SaveView`, `DeleteView`, `SaveGrant` and `Access::fullView()` refuse it; `CopyViews` copies it onto the target's master row.
- `Grant/`: `Grant`, `GrantRepository`, `GrantQuery`, and the use cases `SaveGrant`, `DeleteGrant`.
- `Grid/`: the per-event „Jelentkezők” page (S37). `GridPage` adds the menu (until the admin frame is built: one top-level item per event that is not archived and that the user reaches, ordered by start, with the submenu „Jelentkezők”, slug `kalaka-event-{id}-registrations`), renders the page and enqueues the app. `FieldDefinitions` reads each participant field's type, options, value type and whether it is required (in every form it sits in); `GridModel` orders the columns (Sorszám, Kód, Név, Állapot, then the rest), describes them for the app (a decision column by its kind's declared label and states, else its key and the recorded states), names and keys the tabs (one tab per grant, `g{grant}`; a full-access tab is `v{view}`) and builds the sum row from the field types and the picked members; `ViewsData` is the views list a counting save reads (the stored shape and version); `Translations` hands core's translations of DataViews' strings to the app; `Texts` holds the Hungarian text PHP renders.
- `Rest/GridRoutes`: the grid's read routes under `kalaka-admin/v1` (rows with core's paging headers and sums, each with the `grant` of a grant holder's tab; the views list), each through `Boundary::route()`, gated by `Access::mayReachAdmin()`; they read through a view `Access` hands out. The app's writes are the abilities `kalaka/save-view`, `kalaka/delete-view` and `kalaka/save-master-counts`, run through core's `wp-abilities/v1` run endpoint.
- `app/grid/`: the grid's React app (bundled `@wordpress/dataviews`): the tabs, the „Műveletek” toolbar with „Táblázat másolása”, and the sum row, a second `<tr>` portalled into DataViews' `<thead>`. `format.js` is its pure logic (cells, sums, the copy), tested by Jest. S38: `DetailPanel` (the side panel over the grid, opened from a row: the identifying header and the tabs; it reads the detail route and shows only the parts the read returns), `MoneyTab` (the „Pénzügyek” tab) and `RecordDialog` (the two recording dialogs: a payment, and one refund / correction dialog; they run `kalaka/record-payment`, `kalaka/record-refund` and `kalaka/record-correction` through `api.js`), `StatusMark`, and `money.js`, their pure logic (amounts in fillér, „30 000 Ft”, the balance, the site time zone's days, the dialog's checks), tested by Jest.
- `Cli/AdminSeeder`: the seed's view with a parameter and its grant holder (`kalaka_partner`).
- `FullAccess/`: the use cases `GrantFullAccess` and `RevokeFullAccess`, both through `FullAccessChange` (the checks, the audit of the real old value, the capability written per user after the commit); `FullAccessQuery` (the one holder rule: a user's own capability or a role carrying it, read from `usermeta`); `FullAccessOnActivation`, which runs the grant as the system for the activating user only while nobody holds full access; the profile checkbox (`ProfileField`), the Users column (`UsersColumn`), and their Hungarian `Texts`. deptrac names this folder the "Full access" layer: besides the view query, the only Admin code that may use Registrations' readers.

Entry points: the abilities (`kalaka/save-view`, `kalaka/delete-view`, `kalaka/save-master-counts`, `kalaka/save-grant`, `kalaka/delete-grant`, `kalaka/grant-full-access`, `kalaka/revoke-full-access`), the profile and user-edit screens, the Users list, the per-event „Jelentkezők” page its `kalaka-admin/v1` routes, the registration detail route, WP-CLI `wp kalaka full-access grant|revoke <user>` (`Cli/FullAccessCommand`), and the plugin's activation hook (`FullAccessOnActivation`).
