# Foundation

Runner, audit, clock, Money, evaluation trigger and module registry.

`Api/` holds, by kind: `Module/` (the `Module` interface and `AbstractModule`, `Modules`, `Schema`, `Contributions`: the seeders so far), `UseCase/` (`UseCase`, `AdminUseCase`, `PortalUseCase`, `Context`, `Runner`, `LockLevel`, and the runner's internal `CoarsePermission`, `RunState` and `RunTrace`), `Audit/` (`Subject` and `Correlation`, and the runner's internal `AuditEntry`, `EntryHeader`, `AuditWriter` and `ErrorRecord`), `Database/` (`DatabaseError`: the database's last error as a `KalakaException`), `Repository/` (the bases `Repository`, `EntityRepository` and `AppendOnlyRepository`), `Query/` (the base `Query`), `Seed/` (`Seeder`, the contribution point of sample data, and `Seeding`, what a seeder runs use cases with), `Actor/` (`Actor`, `Side` and the actor classes), `Error/` (the `KalakaException` family), `Money/` (`Money`, `Currency`), and at its root `Clock`, `LoadState` and `LoadFailure`.

At its root, beside `Boot` and `SchemaUpgrader`, `ObjectCache` holds the rows the repositories read; the runner clears it.

`Decision/` holds the decision rule shapes (`DecisionRule`, `DecisionInput`, `Decision`, `Transition`), the registry `DecisionRules`, and the `DecisionRecord` entity with its `DecisionRepository` and `DecisionQuery`. `Evaluation/` holds `Evaluation`, the procedure the runner calls after `execute`, with `RuleFailed`, the use cases `EvaluateRegistration` and `FlagEvaluationFailure`, the `EvaluationFailure` entity with its `EvaluationFailureRepository`, `PeriodicEvaluation` and `EvaluationFailureQuery` (the flagged registrations of the published events).

Tables, created by the schema in `Module.php`: `kalaka_audit_entries` and `kalaka_audit_subjects`, which only the runner writes; `kalaka_decisions`, which only the evaluation writes; `kalaka_evaluation_failures`, which only `FlagEvaluationFailure` writes and every successful evaluation of the registration clears.

`Seed/` holds the seed: `Seed` (the users, then the contributed seeders), `SeedUsers` (one WordPress user per default role, with WordPress functions), `SchemaDrop` (the development drop: drops the tables each module declares in its `Schema`, then recreates every schema through the upgrader), `SeedGuard` (refuses unless the environment type is `local` or `development`) and `SeedFailure`. `Cli/SeedCommand` is the WP-CLI command, registered by `Module::boot()` when WP-CLI is loaded; Boot hands `Module` the modules that passed the version check and the contributions through `Module::collect()`.

`Periodic/` holds the periodic run: `PeriodicRun` (the sweep of the published events through the `TimeRule`s in the `TimeRules` registry, the retries of the flagged registrations, the lock and the last-run time), `PeriodicRunReport`, `TimeRuleInput`, `PeriodicSchedule` (the WP-Cron wiring), `PeriodicRunHealth` (the `admin_notices` warning and the Site Health test `kalaka_periodic_run`, critical when the last completed run is older than 20 minutes or there is none; it only reads the option and the `Clock`) and the admin use case `StartPeriodicRun` (`kalaka/start-periodic-run`, which schedules a run for the next WP-Cron request). The run takes WordPress's upgrader lock `kalaka_periodic_run` (option `kalaka_periodic_run.lock`) and writes the UTC time it swept up to in the option `kalaka_periodic_run_last` (not autoloaded). `Cli/PeriodicRunCommand` is the WP-CLI command, registered with the seed's.

Entry points: `plugins_loaded` boot (`Boot.php`), `kalaka_register_modules`, `wp kalaka seed [--drop]`, `wp kalaka periodic-run`, the WP-Cron hooks `kalaka_periodic_run` (every 5 minutes, on the interval `kalaka_five_minutes`) and `kalaka_periodic_run_now`, which the plugin's deactivation clears, and the `admin_notices` handler and `site_status_tests` filter of `PeriodicRunHealth`. The real-cron call: WP-Cron alone runs the periodic run, driven by page requests. In production, put `define('DISABLE_WP_CRON', true);` in `wp-config.php` and have the host's cron run, every minute, either `php wp-cron.php` in WordPress's root or an HTTP GET of `https://<site>/wp-cron.php?doing_wp_cron`. Which one IVK's host uses is verified at deployment.
