# Foundation

Runner, audit, clock, Money, evaluation trigger and module registry.

`Api/` holds, by kind: `Module/` (the `Module` interface and `AbstractModule`, `Modules`, `Schema`, `Contributions`: the seeders, the site warnings, the field types, the theme adapters and the block hosts so far, read back with `current()`), `UseCase/` (`UseCase`, `AdminUseCase`, `PortalUseCase`, `Context` (with `holdsRegistration()`: whether the run holds a registration's row lock), `Runner` (with `clock()`: the clock its use cases get, for reads outside a use case), `LockLevel`, and the runner's internal `CoarsePermission`, `RunState` and `RunTrace`), `Audit/` (`Subject` and `Correlation`, and the runner's internal `AuditEntry`, `EntryHeader`, `AuditWriter` and `ErrorRecord`), `Database/` (`DatabaseError`: the database's last error as a `KalakaException`), `Repository/` (the bases `Repository`, `EntityRepository` and `AppendOnlyRepository`), `Query/` (the base `Query`), `Seed/` (`Seeder`, the contribution point of sample data, and `Seeding`, what a seeder runs use cases with), `Actor/` (`Actor`, `Side` and the actor classes), `Error/` (the `KalakaException` family, `SiteClosed` among them), `SiteWarning/` (`SiteWarning`, the contract of a standing condition, with `Shown`, `SiteHealth` and `Severity`), `Entry/` (`Boundary`, through which every entry point runs: REST routes are registered only by `Boundary::route()`, WP-CLI command methods run their body in `Boundary::cli()`, WP-Cron handlers in `Boundary::background()` and rendered output in `Boundary::render()`; and `CommandFailure`, a WP-CLI command's own refusal), `Money/` (`Money`, `Currency`), `Time/` (`Instant`: the one conversion between a `\DateTimeImmutable` and the UTC `datetime(6)` storage text, and the parsing of a site-zone wall time or day), and at its root `Clock`, `LoadState` (the boot's outcome, which a module's late check can only add a failure to, with `close()`) and `LoadFailure`.

At its root, beside `Boot` (which registers the site warnings before any module, and logs the load failures, its own and those the late checks added, only when they start or change, on `wp_loaded` at `PHP_INT_MAX` after the late checks (at once when it has already fired), keeping their one fingerprint in the option `kalaka_load_failure`) and `SchemaUpgrader` (whose `UpgradeInProgress` the boot does not log), `ErrorLog` is the only writer of PHP's error log: one line per failure, with the correlation ID and the whole exception chain. `ObjectCache` holds the rows the repositories read; the runner clears it. `LockKey` is how the runner's lock-order guard identifies and orders the row keys the repository bases declare. `Database/Statements` is the only class that runs statements on `$wpdb`: the runner's transactions (each outermost attempt's at READ COMMITTED, set for that transaction only, with the session's lock-wait timeout at 5 seconds around it), savepoints and the reconnect after a failed rollback, and the prepared reads, inserts, updates, deletes and the development drop of the repository and query bases, the audit writer and `SchemaDrop`. `Database/BinlogCheck` answers whether writes under READ COMMITTED would fail (binary logging with `binlog_format=STATEMENT`), read once per instance (Foundation's module and the boot's site warnings hold one each); while it does, the runner refuses every use case before its transaction and the periodic run does not run. `Database/IsolationHealth` is the site warning with the Site Health test `kalaka_database_isolation`, critical while `BinlogCheck` refuses; it only reads `BinlogCheck`.

`SiteWarning/` holds `SiteWarnings` (the registry, the one `admin_notices` banner renderer and the one `site_status_tests` adapter, with the Kaláka badge), and the boot's `LoadFailureWarning` (a banner only, from the request's `LoadState`) and `ErrorLogWarning` (the Site Health test `kalaka_error_log`: PHP's active error log under `ABSPATH`). The boot's warnings, in their order: the failed load, `IsolationHealth`, the error log, `PeriodicRunHealth`; contributed ones follow, errors before info.

`Decision/` holds the decision rule shapes (`DecisionRule`, `DecisionInput`, `Decision`, `Transition`), the registry `DecisionRules`, and the `DecisionRecord` entity with its `DecisionRepository` and `DecisionQuery`. `Evaluation/` holds `Evaluation`, the procedure the runner calls after `execute`, with `RuleFailed`, the use cases `EvaluateRegistration` and `FlagEvaluationFailure`, the `EvaluationFailure` entity with its `EvaluationFailureRepository`, `PeriodicEvaluation` and `EvaluationFailureQuery` (the flagged registrations of the published events).

Tables, created by the schema in `Module.php`: `kalaka_audit_entries` and `kalaka_audit_subjects`, which only the runner writes; `kalaka_decisions`, which only the evaluation writes; `kalaka_evaluation_failures`, which only `FlagEvaluationFailure` writes and every successful evaluation of the registration clears.

`Seed/` holds the seed: `Seed` (the users, then the contributed seeders), `SeedUsers` (one WordPress user per default role, with WordPress functions), `SchemaDrop` (the development drop: drops the tables each module declares in its `Schema`, then recreates every schema through the upgrader), `SeedGuard` (refuses unless the environment type is `local` or `development`); a refusal or failed step is an `Api\Entry\CommandFailure`. `Cli/SeedCommand` is the WP-CLI command, registered by `Module::collect()` when WP-CLI is loaded, with its own clock (so it exists even when Foundation's upgrade failed and `boot()` never ran); `Seed` gets the runner through a factory and asks for it only after the closed-site drop, because `Runner::current()` throws when Foundation never booted. Boot hands `Module` the modules that passed the version check and the contributions through `Module::collect()`.

`Periodic/` holds the periodic run: `PeriodicRun` (the sweep of the published events through the `TimeRule`s in the `TimeRules` registry, the retries of the flagged registrations, the lock and the last-run time), `PeriodicRunReport`, `TimeRuleInput`, `PeriodicSchedule` (the WP-Cron wiring), `PeriodicRunHealth` (the stall warning with the Site Health test `kalaka_periodic_run`, critical when the last completed run is older than 20 minutes or there is none, silent while the load failed or `BinlogCheck` refuses; it names the failing run as the cause when the run's last failure is newer than its last completed run, otherwise cron; it only reads the two options, the `Clock`, the load state and `BinlogCheck`) and the admin use case `StartPeriodicRun` (`kalaka/start-periodic-run`, which schedules a run for the next WP-Cron request). The run takes WordPress's upgrader lock `kalaka_periodic_run` (option `kalaka_periodic_run.lock`) and writes the UTC time it swept up to in the option `kalaka_periodic_run_last` (not autoloaded). A time rule that throws is isolated to its rule and event; the windows it missed, and those of a registration skipped for a retryable failure, are kept in the option `kalaka_periodic_run_missed` (not autoloaded), keyed `<rule name>|<event id>`, until the rule succeeds for that event (dropped once the event is no longer published or the rule no longer registered). `TimeRules::add()` refuses a second rule with the same `name()`. The WP-Cron handler keeps the last failure of a run (UTC time and exception chain) in the option `kalaka_periodic_run_failure` (not autoloaded). `Cli/PeriodicRunCommand` is the WP-CLI command, registered by `Module::boot()` when WP-CLI is loaded.

Entry points: `plugins_loaded` boot (`Boot.php`), `kalaka_register_modules`, `wp kalaka seed [--drop]`, `wp kalaka periodic-run`, the WP-Cron hooks `kalaka_periodic_run` (every 5 minutes, on the interval `kalaka_five_minutes`) and `kalaka_periodic_run_now`, which the plugin's deactivation clears, and the `admin_notices` handler and `site_status_tests` filter of `SiteWarnings`. The real-cron call: WP-Cron alone runs the periodic run, driven by page requests. In production, put `define('DISABLE_WP_CRON', true);` in `wp-config.php` and have the host's cron run, every minute, either `php wp-cron.php` in WordPress's root or an HTTP GET of `https://<site>/wp-cron.php?doing_wp_cron`. Which one IVK's host uses is verified at deployment.
